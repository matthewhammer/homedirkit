## One signature, not two

Cyrus clarified that we want **one LiveLit module signature, not two**. The
functional/macro dichotomy gets captured by a **sum type for the `expand`
member** rather than by having two signatures to answer to.

So `expand` has type:

```
+Functional( Model -> Expansion ) + Macro( Model -> (Exp, List(SpliceRef)) )
```

The top-level type connective of `expand` is a sum. Every livelit commits to
being either functional or macro-based by how it inhabits that sum.

Full words `Functional` and `Macro` for now, until Cyrus or someone else picks
something shorter.

*(Note to self: this replaces the two-signature design I had landed the week
before — `LivelitFun` / `LivelitMac` with `expand_fun` / `expand_mac` members.
The reason I had given for two signatures was that a signature can only say a
member is REQUIRED, so "exactly one of expand_fun / expand_mac" could not be
said inside one signature. A sum type says exactly that, in the member's own
type. It is a better answer to the question I was asking.)*

## Splices as dynamic things

Push forward on this. Splices should be dynamic, not fixed by the program text
the way they are now.

## SpliceRef is not type-indexed

A SpliceRef is **not** associated with the type of the thing it may be holding.
It is just `SpliceRef` — not `SpliceRef(Int)` or similar. Make sure the slides
match this design choice as it exists in Hazel.

*(Note to self: `splice_new` still takes a type argument for the hole it
creates. That is a different thing from the ref itself carrying that type. The
ref stays monomorphic. Check that nothing I wrote in the slides or in
docs/livelits-full.md implies otherwise — I had been describing "a splice gets
a declared type at creation", which is true of the hole and must not be read as
true of the ref.)*

## Livelit errors should be type errors

Wherever possible, livelit errors should surface through the **existing type
machinery** rather than through livelit-specific diagnostics. A livelit
definition is a module; a livelit that does not satisfy the interface is a
module signature mismatch, and should read like one.

The livelit-specific marks today:

| mark | what it says |
|---|---|
| `BadLivelitModel(Typ.t)` | the model argument does not fit, so no expansion could be produced |
| `BadLivelitExpansion({declared, actual})` | the expansion's type is not the declared `Expansion` — the per-use check |
| `InvalidLivelitDef(DefNotModule)` | the definition is not a module |
| `InvalidLivelitDef(DefMissingMembers)` | required value members absent |
| `InvalidLivelitDef(DefMissingTypes)` | required type members absent |
| `InvalidLivelitDef(DefMemberMismatch)` | a member's type disagrees with the signature |

(`IsLivelitName` also exists but is informational, not an error.)

At least the bottom three look like hand-rolled versions of things the module
system already says — Hazel already has `ModuleMissingMembers` and
`ModuleMemberNotFound` as ordinary marks, and a member whose type disagrees
with a signature is an ordinary inconsistency.

This is already happening by accident. Declaring `type Expand` makes
`Functional(f)` checked analytically against `Model -> Expansion`, so a
mismatch now surfaces as a plain *"Expecting type String but got inconsistent
type Model"* at the offending expression, rather than as
`DefMemberMismatch`. That is the direction we want, and it arrived as a side
effect rather than a decision — worth making it a decision.

## Resolved after all: how the constructors get into scope

I had this down as the thing to ask Cyrus about, with three workable forms and
a table of their trade-offs, and a decision to go with a module-local
`type Expand` member pending his view. It turned out not to need asking. The
question was a symptom.

`UserLivelit.detect` was hand-rolling a signature check: realize the
signature's abstract types, look up its members, compare each against the
definition's **synthesized** type with `Typ.is_consistent`. Synthesizing is why
`Functional(f)` had nowhere to get its constructor from, and why a mismatch had
to be reported by a livelit-specific mark rather than by the type system.

A livelit definition now gets a second pass, **analyzed** against the `Livelit`
signature with its own Model, Action and Expansion made *manifest* — realized
rather than as-written, because the signature declares those three abstract and
analyzing against it directly would seal them, and a use of `^name` has to keep
synthesizing Expansion concretely or clients cannot reason about what a use
means.

Analysis supplies the constructors, so `type Expand` is gone from twelve files.
A mismatched member is now an ordinary inconsistency at the member. Eager
definition-site checking, which is what Cyrus asked for, is preserved.

Worth telling him anyway — not as a question, but because the shape of the
answer is the interesting part: the boilerplate was the price of synthesizing,
and nobody had to choose to pay it.

## Still open: eager checking makes the per-use check vacuous

This one is real and I have not resolved it.

With eager definition-site checking, `Functional(f)` is checked against
`Model -> Expansion` where it is written, so `f(model)` has type `Expansion` at
every use — and there is nothing left for the use-site check to catch. The
paper checks per use (S3.2.5) because a **macro** expansion is a program whose
type depends on the model value. A functional livelit typed at its definition
is not that.

So `BadLivelitExpansion` cannot currently fire for a functional livelit. The
machinery stays and becomes load-bearing again when the Macro arm is
inhabitable, which is what `Exp` is for. Two tests record this rather than
pretending otherwise.

Whether moving off the paper's per-use strategy for functional livelits is
intended, or whether he would rather keep the definition-site check weaker so
the per-use one still does work, is his call.

## After the meeting: what building it turned up

Everything above is the meeting. This part is not — it is what came out of
starting the `expand`-as-a-sum change the same afternoon, recorded here because
it bears on the design and I would otherwise lose it.

**The constructors have to be in scope, and by default they are not.** Writing
`let expand = Functional(fun m : Model -> m)` fails with *"Constructor is not
defined"*. The signature declares `expand`'s type, but that does not put
`Functional` and `Macro` into the definition's namespace.

Worse than a plain error: while the constructor was unresolved, **both the
definition-site and the use-site expansion checks silently stopped firing.**
Four tests caught it. Those checks are the paper's per-use obligation and the
whole point of the work, so a design that quietly disables them would have been
a bad thing to merge.

Three forms work, all measured with the CLI:

- annotate `expand` with the whole sum at every livelit — verbose;
- declare `type Expand = ...` as a member of each livelit — repetitive;
- register the sum as a **global type alias**, which puts its constructors in
  scope the way `Ord` puts `Lt` there. Authors then write `Functional(f)` with
  no annotation and no extra member.

I tried the global alias first, because it is the only one that costs the
author nothing. It resolves the constructor and then fails to catch the
mismatch: its arms have to be unknown, since Model and Expansion are
per-livelit while the alias is global, so the function's real type is widened
away. Went with the module-local declaration next.

**None of the three was the answer.** All three are ways to make *synthesis*
work, and synthesis was the problem — see the resolved section above. Leaving
the list here because it is how I got there, not because one of them is what
shipped.

**One ergonomic cost of the design, worth knowing.** `expand` can no longer be
written in funlet form: `let expand(m) = ...` does not typecheck, because
`expand` is not a function any more — it is a sum with a function inside. The
member you most want to write as a function is the one that cannot be. `update`
and `view` keep the sugar.

**Use sites now have to discriminate.** `^name.expand` hands back the sum, so a
client reading it says `case ^name.expand | Functional(f) => f(m) | Macro(_) =>
... end`. That is arguably the point — the kind is visible in the value rather
than in which signature the definition answered to.
